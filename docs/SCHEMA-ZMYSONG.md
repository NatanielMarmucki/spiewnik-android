# Schema of the old Core Data database (iOS)

Written down from a database generated by the Swift app in the simulator.
File on the device: Documents/Model.sqlite

The migration in `lib/migration/` reads this database once, when the Flutter app replaces the old iOS app.

## ZSONG

CREATE TABLE ZSONG (
  Z_PK INTEGER PRIMARY KEY, Z_ENT INTEGER, Z_OPT INTEGER,
  ZFAVORITE INTEGER, ZNUMBER INTEGER, ZCONTENT VARCHAR, ZTITLE VARCHAR
)

- ZFAVORITE: 0 or 1
- ZNUMBER: song number, 1-2000
- ZTITLE and ZCONTENT are optional in the Core Data model and can be NULL

## ZMYSONG

CREATE TABLE ZMYSONG (
  Z_PK INTEGER PRIMARY KEY, Z_ENT INTEGER, Z_OPT INTEGER,
  ZCONTENT VARCHAR, ZTITLE VARCHAR
)

- No date columns at all. The migration sets createdAt and updatedAt
  to the time of the migration.
- ZTITLE and ZCONTENT are optional and can be NULL.
- The table exists even in a fresh database: Core Data creates it on the first
  launch of the app. It is missing only from the template file
  in the iOS repository (test/fixtures/ios_no_mysong.sqlite).

## Z_ENT — confirmed values

Databases from a device (ios_fresh, ios_with_data):
- Z_PRIMARYKEY: MySong = 1, Song = 2
- ZSONG: Z_ENT = NULL in every row (seeded from the bundle),
  even though Song = 2 is assigned
- ZMYSONG: Z_ENT = 1, as in Z_PRIMARYKEY

Template from the iOS repository (ios_no_mysong):
- Z_PRIMARYKEY: Song = 1, no MySong entity
- entity numbering differs from the device databases

Conclusion: do NOT filter by Z_ENT in any table. Entity numbering is not
stable between the template and a database created on a device.
